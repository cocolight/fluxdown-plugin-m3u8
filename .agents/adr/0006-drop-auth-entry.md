# 移除登录入口，凭据改由设置项直供

- 状态：已接受
- 日期：2026-11-01
- 决策者：fluxdown-plugin-m3u8 维护者

## 背景

插件自 v1.6.0 起声明 `auth` 入口，宿主的规矩是：**声明了 `auth.entry` 就在「设置 → 扩展 → 插件」里该插件那一行加一个「登录」按钮**
（官方《认证指南》）。点开的对话框有两个输入框 ——「站点」与「登录信息」 —— 用户填完，
插件把凭据规范化成档案，经 `flux.auth.save` 存进宿主的凭据库，按 `插件ID::站点` 引用。

这套模型的前提是**插件对应固定站点**。本插件的 resolver 匹配的是全通配 URL（`*://*/*`），
一个通用解析器被塞进按站点登录的框里，产生三个具体问题：

1. **对话框的「站点」必须由用户填，但没人知道该填什么。** 用户是从设置页看到按钮的，
   那里没有任何「站点」概念；不填就走 `begin` 的无输入分支，得到
   「缺少站点信息：请在「设置 → 插件」里填写站点后再登录」—— 而**根本不存在这个设置项**。
2. **「登录信息」与「登录凭据」两个入口要用户做同一件事**：粘贴 Cookie / token。
   一个是对话框，一个是设置里的 textarea，后者还带「复制取 Cookie 的脚本」按钮。
3. **凭据的作用域被绑在一个用户手填的站点上**，填错站点 → 凭据永远不生效，且没有任何提示。

## 决策

1. 删除 `manifest.auth` 段与 `permissions: ["auth"]`，删除 `src/entry/auth.ts`。产物从六个入口降到五个。
2. 凭据**只从设置项 `authCookie` 读**（`src/lib/credential.ts` 解析成请求头）：
   - 下载补丁：进 `request.originHeaders`，origin 取**任务 URL**（`ctx.url`）的 origin；
   - 抓取：`lib/http.ts` 的 `fetchHeaders` 按同一条同源闸附加。
3. 同源闸保留：目标 origin 与任务 URL 的 origin 不一致时整条不注入并记日志。
   这样「清单在站内、分片在 CDN」的常见形态下，Cookie 仍然不会发给 CDN —— 与 v2.x 的实际效果一致，
   区别只是「登记站点」的来源从对话框输入变成任务地址本身。

## 后果

- 正面：设置里少一个按钮、少一个权限；用户只需要在一个地方粘一次凭据；不再有「填站点」的死路。
- 负面，两条都要认：
  1. **老用户的登录态失效**。v2.x 经对话框存进宿主凭据库的档案不再被读取，
     升级后需要把凭据重新粘贴到「登录凭据」设置项。这是 breaking，故版本号取 3.0.0。
  2. **凭据不再是「按站点管理」的一等公民**：宿主凭据库的过期时间、注销、按站点隔离都不再适用。
     插件侧只做「一段文本 → 一组请求头」，过期与轮换由用户自己维护。
- 门禁变化：`tests/parity/scenarios.mjs` 里 13 条 `auth` 场景随功能删除；凭据注入的 3 条改为
  `authCookie` 驱动并声明 `diverges`。删除本身由 `tests/contract.mjs` 断言
  （manifest 无 `auth` 段、权限无 `auth`、产物无 `auth.js`），不是「删了测试当没事」。

## 备选方案

- **保留 auth 入口，只改文案**：仍然要用户在对话框里填一个他自己都不知道的站点；治不了根。
- **`location: "auth"` 自定义登录界面**：可以让对话框变成「只粘凭据」的样子，
  但凭据仍要绑定一个站点才能入库，问题 3 依旧；且要多维护一个视图。
- **让 `begin` 在无站点时把凭据回写进 `authCookie` 设置**：能用，但等于用登录对话框做设置页的事，
  两套入口并存，用户更难理解。
