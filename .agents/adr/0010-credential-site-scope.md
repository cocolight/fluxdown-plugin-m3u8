# 凭据自带站点约束，判断下沉到解析层

- 状态：已接受
- 日期：2026-11-03
- 决策者：fluxdown-plugin-m3u8 维护者
- 关系：修订 [ADR-0006](0006-drop-auth-entry.md) 的决策第 3 条（同源闸的效力描述有误，闸本身保留）

## 背景

ADR-0006 用「任务 URL 的 origin」代替登录对话框里用户手填的站点，并宣称同源闸能挡住
「清单在站内、分片在 CDN」这路泄漏。**这个说法是错的**，实测暴露：

`src/lib/request.ts` 的 `credentialOrigin()` 把 `ctx.url` 的 origin 同时用作「凭据归属站点」和
「同源闸的另一侧」：

```ts
const site = safeOrigin(ctx.url);   // 归属站点
...
const cred = parseCredential(raw, site);  // 内部按 site 建 origin
if (!cred || credentialOriginsEqual(cred.origin, safeOrigin(ctx.url))) ...
```

两侧都取自 `ctx.url`，等式**恒成立** → 闸门等于没有。真机上拿三个不同 hostname
（`localhost` / `127.0.0.1` / `cdn.localhost`）指向同一端口把同一个任务建三次，
三份都拿到了 Cookie；清空 `authCookie` 后三份全空，证明注入确实来自插件而非别处。

同源闸本身是有价值的（它挡住了「分片换到 CDN 域」这一路），坏的是它被当成了
「站点归属校验」，而站点归属从来没有来源。

还有一个被忽略的层面：`authCookie` 是**全局单值**，不绑定任何站点。用户为一台 NAS 粘的
Cookie，在这个模型下对每一个被解析的 URL 都有效 —— 只要那 URL 的清单与分片同源。
通用解析器（resolver 匹配 `*://*/*`）天然会遇到大量陌生站点，这不是理论风险。

## 决策

1. **凭据文本首行可写 `@站点`**，声明这份凭据属于谁。语法：

   | 写法 | 含义 |
   | --- | --- |
   | `@a.com` | 裸域 `a.com` 及其所有子域 |
   | `@*.a.com` | 只匹配真子域（不含裸 `a.com`），与浏览器 Cookie 域匹配一致 |
   | `@https://a.com` | 精确到 origin，`http://a.com` 不算 |
   | `@a.com, b.com` | 逗号（含全角）或空白分隔多个 |

   不写 `@` 行 = 不额外限制，行为与 v3.0.0 之前完全一致（向后兼容，不收紧老配置）。

2. **判断下沉到 `parseCredential()`**，站点不命中直接返回 `null`。理由：三条链路
   （抓清单 `lib/http.ts`、下载补丁 `lib/request.ts`、yt-dlp 委派 `lib/ytdlp.ts`）全部
   经这一个入口；逐点加检查迟早漏一条，而漏掉的那条就是泄漏口。解析层是唯一收口点。

3. **站点与凭据必须写在同一个文本框里**，不另开设置项。分开写时用户换站只改一处，
   会出现「新 Cookie 配旧站点」的错配 —— 比没有约束更危险，因为用户会以为已经约束住了。

4. 同源闸**保留不动**，与站点约束是两道独立的检查：站点约束回答「这份凭据属于谁」，
   同源闸回答「这次请求的对象是不是任务所在站点」。

## 后果

- 正面：
  - 泄漏口关闭。真机验证（三个 hostname 打同一 server，端口相同）：

    | 约束 | `localhost` | `127.0.0.1` | `cdn.localhost` |
    | --- | --- | --- | --- |
    | `@localhost` | 注入 | 拦下 | 注入（子域，设计如此） |
    | `@*.localhost` | 拦下 | 拦下 | 注入 |

  - 「复制取 Cookie 的脚本」按钮同步升级为输出 `@' + location.hostname + '\n' + document.cookie`，
    新用户开箱即带约束，不需要理解语法。
  - 契约测试从 47 项增到 58 项，覆盖四种写法 × 命中/不命中 × 无约束兼容，
    以及 yt-dlp 委派链路。

- 负面，两条都要认：
  1. **默认仍不约束**。为了不破坏老用户配置，不写 `@` 行时行为照旧。也就是说老用户升级后
     漏洞依然存在，只有主动更新凭据（或重新点一次复制脚本）才收得紧。这是刻意的取舍：
     强行给旧文本推断站点只能靠猜，猜错会让用户「升级后突然登不上」。
  2. **语法藏在文本框里**，没有独立 UI 提示。用户手写时可能写错（例如把 `@https://a.com/path`
     写成带路径的形态，当前会按 origin 处理并忽略路径）。设置项 `description` 与
     `docs/settings.md` 已写明，但不如一个可视编辑器直观。宿主的 `SettingField` 是
     `deny_unknown_fields` 且没有 section/group，做不出结构化的站点子表单。

- 门禁变化：`tests/contract.mjs` 新增 2b 节 8 条 + yt-dlp 块内 3 条。注意反例不能用
  `cdn.site.test` —— 它是 `site.test` 的子域，按设计本就该命中，用它当反例会得到假阴性。

## 备选方案

- **新增设置项 `authCookieSite`**：两处输入要用户同步维护，换站时容易只改一处；
  且空值语义含糊（空 = 不限制？还是 = 全部拦下？）。
- **给 `authCookie` 加默认约束为「首个使用它的站点」并粘住**：自动学习看着聪明，
  实际会把用户在多站之间来回切时的行为变成「第一次用谁就锁死给谁」，更难解释。
- **不做站点约束，只在文档里警告**：把安全问题退化成文档问题。通用解析器的场景下
  用户根本不知道这份 Cookie 会飘向哪里，警告起不到拦截作用。
- **依赖宿主凭据库（恢复 ADR-0006 之前的 `auth` 入口）**：宿主凭据库确实是按站点存的一等公民，
  但对话框强制用户填站点，而本插件用户不知道填什么 —— 这正是 0006 要解决的问题。
