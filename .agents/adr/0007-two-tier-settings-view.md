# 设置页分「常用 / 专业」两档

- 状态：已接受
- 日期：2026-11-01
- 决策者：fluxdown-plugin-m3u8 维护者

## 背景

插件有 28 个设置项。宿主的「基础设置」页签是把 `manifest.settings[]` **平铺**成一长列表单：
28 行、原来的描述合计 2767 字，一屏看不完。用户的原话是「设置是给用户看的，现在太复杂」。

先确认引擎能做什么、不能做什么。上游 `native/engine/src/plugin/manifest.rs` 的声明式设置项：

```rust
#[serde(rename_all = "camelCase", deny_unknown_fields)]
pub struct SettingField {
    key, title, description, ty, widget, options, default, required, min, max, pattern, helper_script, helper_label
}
```

**没有 `group` / `section` / `advanced` 之类的字段，而且是 `deny_unknown_fields`。**
结论：宿主的表单**无法分组、无法折叠**，条目只能靠 manifest 里实际存在多少项决定。
「默认简单、需要时展开」这个交互只能做在插件自己的视图里（`contributes.views` 的 `settings` 页签）。

## 决策

1. **视图做两层**：默认渲染 12 项常用（画质、自动选最高画质、命名、登录凭据、UA、额外请求头、
   音轨、纯音频、转 MP4、yt-dlp 兜底、去广告模式与规则）；打开「显示专业设置」后追加 16 项
   （站点适配、剧集识别、编码、下载行为）。开关状态存进设置项 `expertMode`，下次打开保持上次的选择。
2. **manifest 侧只做两件不改变能力的事**：改写 28 项的标题与描述为面向使用者的一句话
   （总字数 2767 → 711），并按「常用在前、专业在后」重排。**不删任何设置项** ——
   引擎不允许条件渲染，删掉就无法在专业模式里改回来。
3. **保存语义改成「只写改动过的键」**：28 项的草稿一次性回写会把用户在别处（基础设置页签、
   别的视图实例）改过的值覆盖回去。

## 后果

- 正面：默认状态下一屏能看完；专业项仍在，不需要「删设置 → 想要又加回来」的往返。
- 负面，三条：
  1. **基础设置页签仍然是 28 项**。视图的分层不会改变宿主表单 —— 只要用户点「基础设置」，
     看到的还是平铺列表（顺序上常用项在前）。这一点在 `docs/settings.md` 里写明，不假装解决。
  2. **视图硬编码了 28 个 key 与四个 select 的 options**。manifest 改键名或选项而视图没跟上，
     用户会收到宿主的「未知设置项」或值被回退。`tests/ui.mjs` 用两条断言顶住：
     「每个 select 的当前值都在自己的 options 里」与「manifest 声明的 key 都能在页面上找到」。
  3. 视图变大了（`dist/main.js` 17.2 → 27.5 KB）。仍是纯本地渲染，不发请求。
- 门禁：`tests/ui.mjs` 从 37 项增到 43 项，新增 6 项专测两档（默认不漏专业项、打开后出现、
  开关即时展开、选项不漂移、键集合与 manifest 一致）。

## 备选方案

- **只改文案不改结构**：28 项还是 28 项，用户的原问题（太复杂）没动。
- **删掉 15 项纯调参设置，全部硬编码默认值**：能一次降到 13 项，但改过这些项的用户的配置会回落到默认，
  且日后想调回来就得改代码 + 发版。在「专业模式」可行时，删除是净损失。
- **把专业项塞进一个 JSON 文本框**：设置项数量降下来了，但用户要手写 JSON 才能改「内嵌跟进几层」，
  比现在的 28 项更难。
